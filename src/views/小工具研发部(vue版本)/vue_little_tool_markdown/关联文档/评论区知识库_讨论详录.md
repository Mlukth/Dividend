## 一、竞品研究全过程

用户的指令："深度搜索和使用tavily去搜索相关信息，参考现成的方案，信息检索这种东西并不是很稀有的东西"

### 第一轮搜索（3个方向并行）

**搜索1**：`prompt engineering extract key points from social media comments structured JSON output`
- 找到：Structured Output最佳实践（schema+rules+examples+validation四层法）
- 找到：JSON输出的关键规则（低temperature、refusal rules防幻觉、missing fields用空值不用null）
- 找到：Prompt Engineering for Structured Output（Nature论文级别的方法论）
- **结论**：结构化输出有成熟方法论，核心是schema定义+严格格式规则+范例+验证

**搜索2**：`build personal knowledge base from video comments classification tagging system open source`
- 找到：Open-source knowledge base工具（Outline/Docmost/Logseq等），但都不做评论提取
- 找到：PKM社区讨论（Forte Labs的Complete Guide to Tagging、Obsidian论坛的tagging best practices）
- 找到：Bookshelf（开源AI知识库，RAG方案）
- **结论**：PKM工具成熟，但"评论→知识库"这条链没有现成的

**搜索3**：`comment analysis pipeline NLP extract viewpoints cluster opinions information retrieval`
- 找到：ABSA（Aspect Based Sentiment Analysis）学术领域，相关但不直接匹配
- 找到：NLP Pipeline方法论（数据采集→清洗→特征工程→建模→评估）
- 找到：customer review analysis的三种方法（数据挖掘/情感分析/主题建模）
- **结论**：学术和工业都有相关技术，但都是分析工具，不做个人知识库积累

### 第二轮深挖（3个方向并行）

**搜索4**：`prompt template summarize discussion thread extract different viewpoints opinions structured format`
- 找到：Canvas Discussion Summaries（教育领域的讨论摘要功能，概念接近）
- 找到：OpenAI论坛的"长文本摘要+结构化提取"讨论——分块+refine方法
- 找到：Reddit上的"Chat Summary to Markdown"提示词模板（结构类似：objectives→key actions→decisions→insights→next steps）
- **结论**：有可参考的讨论摘要模板，但都不针对评论区场景

**搜索5**：`PKM personal knowledge management tagging taxonomy best practices`
- 找到：Forte Labs的A Complete Guide to Tagging（层级vs网络、ambient findability、渐进式标签）
- 找到：Obsidian社区tagging方案（broad categories/status/process/topic-based/nested tags）
- 找到：Dovetail的taxonomy best practices（定期审计、防标签膨胀、命名空间）
- 找到：Better Tagging Practices for PKM（命名空间`status/`、`topic/`，CSS可视化）
- **关键收获**：标签服务于使用场景不服务于归档；层级做粗分类标签做跨域连接；起步从简渐进收敛

**搜索6**：`open source tool analyze youtube bilibili comments extract insights github`
- 找到：**commentpulse** — Chrome扩展，B站+YouTube评论分析，用DeepSeek，开源前端+私有后端。功能：评论分析/弹幕分析/趋势追踪/竞品对比。API端点：/analyze /competitor /improvement /trend
- 找到：**starseeker** — Chrome扩展，小红书+Reddit评论抓取导出CSV，20个字段含评论内容+IP属地+点赞数。v2.0.0支持GPT分析
- 找到：**bilibili-summary** (jackwener) — AI视频摘要，ASR+LLM，面向视频内容不做评论
- 找到：GitHub topic `comment-analysis` 共7个仓库，覆盖采集/导出/分析但都不做知识库
- **关键收获**：commentpulse架构（扩展→后端→AI Provider）可参考；但无工具做"评论→观点→分类→知识库→检索"

### 竞品差距总结

| 工具 | 做什么 | 缺什么 |
|------|--------|--------|
| commentpulse | 评论分析(趋势/情绪/竞品) | 不提取观点、不做知识库、不提供检索 |
| starseeker | 评论抓取导出CSV | 纯采集工具，AI分析浅，不做分类存储 |
| bilibili-summary | 视频摘要 | 面向视频内容，不做评论 |
| PKM工具(Obsidian/Logseq) | 笔记管理 | 不做评论提取，需要手动录入 |

**结论：无现成方案。值得自建，但可以大量参考commentpulse的架构和ETT的双模式设计。**

## 二、提示词设计迭代

### v1（初始版）

基于用户的参考提示词："干两件事，提取核心要点 + 不修改原文分段 + []包裹小总结 + 末尾汇总"

设计要点：
- 任务A输出人类阅读版（分段+[标签]）
- 任务B输出JSON（机器可读）
- **包含过滤逻辑**：纯表情/"666"/"谢谢UP"等过滤掉，末尾列出

用户反馈后实测了7个考研评论楼层。

### v2（当前版）

用户反馈修改：
- **过滤逻辑去掉** → 改为"全部保留不丢失"，低信息量内容用`[感谢][表情回应][附和]`标记但不删除
- 新增 `infoValue` 字段（1-5分）区分信息价值，替代过滤
- 新增 `completeness` 字段标记楼层是否完整（"共3条回复"但未展开）

### 提示词跨平台设计

参考ETT的双模式：
- **API模式**：直接调DeepSeek → JSON自动入库
- **窗口AI模式**：一键复制`提示词+评论原文` → 粘贴到ChatGPT/Claude → AI返回JSON → 粘贴回来 → 解析入库

提示词存储：JSON文件（`comment-kb-prompts.json`），参考ETT的`ett-prompts.json`。支持UI编辑+保存+代码常量兜底。

## 三、UI方案对比详情

用户指令："多写几个那这里只有a b c 写个cemet efg都可以 我挑1个我觉得可以的就行"

参考文件：`src/views/组件测试/ETT-mobile-弹窗适配方案-DEFG.vue`（该文件展示D~H共5套手机端弹窗方案，含对比表+推荐）

### 5套方案设计

| 方案 | 布局 | 输入区 | 结果展示 | 线程管理 | 知识库浏览 |
|------|------|--------|----------|----------|------------|
| C 左右双栏 | 左42%输入 右58%结果 | 大文本框 | Tab切换阅读版/JSON/统计 | 无 | ⭐⭐ 一次看一个 |
| D 上下分屏(ETT风格) | 上45%输入 下55%结果 | 可切换为楼层列表 | Tab切换 | 简单列表 | ⭐⭐ 可切换楼层 |
| E 三栏工作台 | 左22%浏览 中50%详情 右28%JSON | 中栏顶部输入 | 中栏阅读版+右栏JSON同屏 | 话题树+标签云 | ⭐⭐⭐⭐ 最佳 |
| F 卡片流 | 顶部紧凑输入条+卡片流 | 紧凑输入条 | 可折叠卡片 | 每楼层一张卡 | ⭐⭐⭐⭐⭐ 最佳浏览 |
| G 极简单页 | 三步流程：粘贴→处理→结果 | 大文本框 | 步骤3展示 | 无 | ⭐ 无浏览 |

### 用户选择：方案E

理由：三栏同屏，话题树+观点列表+详情+JSON全部可见，适合重度使用。

### 关键修正：观点为最小单位

选择方案E后用户追加修正："不太想让他这个以楼层为最小单位啊 因为最小单位嘛然后围绕这些观点有什么东西才对吧"

**数据模型重构**：
- 之前：Thread → Viewpoint（观点附属于楼层）
- 之后：Viewpoint 是原子单位，source.threadId 只是出处元数据
- 影响：左栏话题树/标签云按**观点**聚合，不按楼层；搜索搜的是观点不是楼层；同楼层其他观点作为"来源上下文"展示在中栏

## 四、数据模型设计讨论

### 观点（Viewpoint）字段设计

```
{
  id,                    // 唯一标识
  speaker,               // 说话人
  speakerRole,           // UP主|评论者|提问者
  tag,                   // [观点标签] 5-10字
  original,              // 原文不修改含表情
  stance,                // 支持|反对|中立|提问|补充|感谢
  infoType,              // 个人经验|事实陈述|推测|建议|辟谣|提问|社交互动
  infoValue,             // 1-5 信息价值评分
  topics: [],            // AI自由打标的话题
  source: {              // 出处（非主体，仅元数据）
    threadId, platform, videoTitle, up主, date, completeness
  }
}
```

### 为什么infoValue要替代过滤

用户从"过滤无用内容"改为"全部保留不丢失"的理由：
1. 丢了就没了，以后想回溯也没办法
2. 低信息量内容也可能有上下文价值（比如看舆论氛围）
3. infoValue评分让用户自己决定看什么，不替用户做删除决策

infoValue评分标准：
- 5: 一手数据/具体案例/可操作建议
- 4: 有依据的分析推理
- 3: 有参考价值的个人看法
- 2: 泛泛而谈
- 1: 纯社交互动/表情/感谢

## 五、分类方案设计讨论

用户选择：**AI自由打标**（不用预设分类树）

### 理由
1. 预设分类树装不下新话题——评论区话题高度不确定
2. AI自由打标灵活，什么话题都能标
3. 积累一段时间后，人工review高频tag，收敛为正式分类
4. 低频tag自然淘汰或合并

### 参考PKM最佳实践
- **Forte Labs**：标签服务于使用场景，不服务于归档。层级做粗分类，标签做跨域连接
- **Obsidian社区**：命名空间标签 `topic/考研择校` `stance/支持` `infoType/个人经验`
- **Dovetail**：定期审计（6个月），高频tag保留，低频合并
- **渐进收敛**：起步不管→积累→发现规律→收敛→再积累→再收敛

## 六、存储方案讨论（未最终确定）

参考ETT的JSON文件+API中间件模式：

```
public/comment-kb/
├── viewpoints.jsonl      # 所有观点扁平存储（便于统计和检索）
├── threads/              # 原始楼层存档
│   └── {threadId}.json
├── sources.json          # 视频来源索引
├── tags.json             # 标签字典 {tagName: {count, category, aliases}}
├── stats/                # 统计快照
│   └── {sourceId}_stats.json
└── prompts.json          # 提示词（即comment-kb-prompts.json）
```

API端点（参考ETT的vite中间件）：
- `GET /api/comment-kb/viewpoints` → 读取所有观点
- `POST /api/comment-kb/viewpoints` → 追加新观点（防覆盖，读-合并-写）
- `GET /api/comment-kb/stats` → 统计摘要
- `GET/POST /api/comment-kb/prompts` → 提示词读写
